# 9.2.12 — Retain original foreign purchase, confirm account settlement

Phase remains OPEN. This batch uses the existing transaction, correction, backup,
mutation guard and reporting paths; it does not create a parallel ledger.

A trusted, completed purchase linked to an existing card may be explicitly retained
by its owner before the account-currency principal is known. It keeps its original
amount/currency, card, event identity and evidence, with `settlementStatus: pending`,
null wallet amount and null FX rate. It contributes no guessed account movement.
The balance, affected report total, transaction average and remaining overall budget are unknown, and the report shows the count
and original amount of purchases awaiting settlement. No account is created for
the purchase currency. Existing historical records are not silently changed.

Opening this purchase requires confirmation of the account-currency principal,
separate fees (including an explicit zero), and the same purchase/card. The durable
mutation replaces the same transaction and appends a settlement audit. Its original
amount, currency, account/card, creation time and import identity cannot change in
this transition. Failed durable storage rolls back; retry keeps one event and audit.
Schema 16 optional fields survive full backup, strict restore and normalization.

## Acceptance and limits

- Synthetic MAD/EUR/USD purchases on AED and USD purchase on EGP credit cover
  pending and confirmed paths, without currency relabeling or guessed balances.
- One pending EUR purchase is exported/restored/reloaded, then settled with separate
  fees. Replaying confirmation cannot overwrite the confirmed settlement.
- Simulated quota failure retains identical live/durable pending state; retry posts
  once. This does not prove actual Android disk-exhaustion behavior.
- Actual browser DOM/IndexedDB flow saves pending purchase, displays incomplete
  report, reloads, confirms principal/fee, reloads and repeats SMS scan without a
  second purchase. All 28 browser checks passed locally in Chromium 151.
- All 48 JS test files are required, including the new pending-settlement test.
  The credit report assertion now checks the added zero pending count while keeping
  its original principal/repayment expectations.
- Browser performance setup initially raced startup scanning and received the
  exclusive-operation busy rejection. Waiting for all actual financial/import busy
  flags and boot-splash completion fixed setup; no assertions or timeout limits were removed.
- A later local rerun exposed the receipt editor opening while the previous sheet
  was still closing. Its screenshot showed the home screen despite editor DOM.
  Setup now waits for the existing stable-home condition before reopening. The
  receipt save, reload and fingerprint checks remain. Correction setup also waits
  for the completed bank-inbox view, since durable commit finishes before native
  acknowledgement and the final review-screen refresh. The new average assertion
  accepts the actual Arabic or English heading because the test switches language.

The acceptance subset above has zero guessed postings and zero second purchases;
it is not a financial accuracy rate for the private SMS corpus or worldwide banks.
Native process death, Samsung S25 FE, real notification/SMS concurrency, actual
disk exhaustion and biometric behavior remain device acceptance work.
