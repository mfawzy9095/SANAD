# 9.2.13: settlement evidence, learning controls and durable import

This is a continuation, not closure of the full financial QA scope. No user SMS, backup, account identifiers, screenshots or signing secrets belong in this repository.

## Financial contract

A completed settlement can update an existing pending purchase only when trusted bank source, account, instrument, original reference, original date, original currency and exact original minor-unit amount identify exactly one event. The settlement explicitly names the principal excluding fees and a separate fee in the account currency. Missing/ambiguous evidence stays in review. A changed settlement or a manually confirmed settlement cannot be overwritten automatically. The original amount/currency and event ID remain unchanged; the update has evidence and an audit entry. Reverse order stays in review until explicitly resolved, rather than creating another purchase.

The first supported settlement grammar deliberately requires explicit labelled original and settlement fields in Arabic or English. It is not a claim to understand every bank's settlement notice. No inferred FX rate or available balance is used as the debit.

Learning controls show and revoke individual source aliases, account identity bindings, message templates and account/currency-scoped merchant classifications. Reactivation of a template or account identity applies prospectively. Existing financial history is not reinterpreted. Controls and their audit use the existing verified financial storage and full backup.

## Import durability and measured work

Historical pages stage their financial decisions privately and commit once per page using the existing verified mutation service. A concurrent state change rejects the stale batch. Evidence acknowledgement and the resume cursor follow durable decisions. A full disk rolls the page back and keeps evidence available for retry. The synthetic 20-purchase regression demonstrates one verified financial write instead of one per purchase; it is not a device speed claim.

Progress is a small panel across tabs. Counts and range are actual values; total comes from the native SMS cursor once per run. Estimated remaining time requires observed progress and is labelled approximate. Read, parse/plan, save and render milliseconds are recorded separately. Completion of reading is distinguished from financial review.

A user-started Android dataSync foreground service displays a private progress notification with pause/cancel controls. A bounded wake-lock lease is renewed after durable progress. Service shutdown, timeout and task removal stop the foreground operation. It is not sticky and does not claim to execute JavaScript after process death: reopening resumes the saved cursor. Notification permission or foreground-start failure leaves the visible-app path usable without promising background execution.

Engineering decisions use primary Android documentation:

- [Foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types): local import is dataSync; declare its type and permission, no boot launch.
- [Launch](https://developer.android.com/develop/background-work/services/fgs/launch): start while user is in the app and promote the service immediately.
- [Timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout): handle Android 15 timeout and stopSelf, preserving the durable checkpoint.
- [WebView.onPause](https://developer.android.com/reference/android/webkit/WebView#onPause()): it does not pause JavaScript. This service keeps the live Activity/WebView operation eligible while backgrounded; process recreation is a separate resume path.
- [ContentResolver query limit](https://developer.android.com/reference/android/content/ContentResolver#QUERY_ARG_LIMIT): provider support is not assumed; cursor date/ID bounds remain authoritative.

## Verification and remaining limits

New red/green core regressions cover same-event settlement, fees, missing identity/amount, conflicting proof, user correction, repeat SMS/notification, reverse order, failed storage and retry. Full-backup validation preserves settlement evidence and revoked identities. Learning tests cover scope and prospective reactivation. Browser tests cover the real correction, settlement and learning screens, persistence and reports. Native CI adds an actual SMS-provider/foreground-service/HOME test; its result must be recorded against the final commit, not assumed here.

Still requiring separate closure: Samsung S25 FE process-kill/notification-action and biometric/attachment testing (actual process kill/reopen passed separately on Android 35 emulator); broad official licensed logo coverage and remaining emoji/picker consistency; bank-specific settlement grammars beyond the conservative explicit contract. Stable QA certificate availability must be verified separately. No historical backup repair is justified without proved ownership and settlement data.

## Brand-source review (2026-10-07)

Official sites expose ENBD horizontal SVG, Emirates Islamic header PNG, du Pay header PNG and e& money common-logo SVG. These were identified from the issuers' own pages, not an aggregator. No blanket redistribution permission was established. [du Pay terms](https://dupay.ae/en/terms), sections 7.10 and 12, restrict content copying/sharing and grant a personal application licence; [e& money terms](https://www.eandmoney.com/en/more/terms-conditions.html), section 16.1, require prior written consent for website-content reproduction. [ENBD terms](https://www.emiratesnbd.com/en/terms-and-conditions) did not establish a reusable logo licence. Therefore these assets are not redistributed here. Existing neutral initials remain offline and labelled; official brand coverage, including Egyptian banks, remains partial. This is an implementation choice to respect the user's source/usage-terms constraint, not a claim that trademarks can never be used descriptively.

Review/import controls now use a small locally authored, consistent stroke SVG set with visible text labels. The exact linked card uses the bank's short registry name inside its existing real-account group. No records are merged, and no network is inferred from last four digits. The remaining application-wide emoji migration is not claimed complete.

An additional synthetic regression exposed an Egyptian credit-card adapter retaining the purchase amount and identity but losing its printed English `on D/M/Y HH:mm` date. Four-digit years were rejected and two-digit years fell back to receipt date. The adapter now extracts the printed date/time, validates the calendar, and anchors a short year to receipt evidence; invalid dates remain review. The regression uses an actual Egypt-country EGP credit account, a trusted Egyptian bank source and a USD purchase, not a preconstructed UAE route. Previously saved history is unchanged.
